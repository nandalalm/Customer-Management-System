# Advanced CRM Dashboard — Staged Implementation Plan

---

## Execution Rules (Must Follow)

These rules govern how the implementation is carried out. They are not optional.

### Batch Size = One Stage
Each stage is deliberately sized to be **one natural commit** — small enough to review and push in a single sitting, large enough to be meaningful progress.

- **Do not combine stages.** Do not deliver Stage 2 and Stage 3 together.
- **Do not split a stage mid-way** and leave files in a broken state.
- Every stage must leave the codebase in a **working, non-broken state** when it ends.

### After Every Stage
1. Stop completely.
2. List every file that was created or modified.
3. One sentence on what this stage accomplished.
4. Tick off the completed checkboxes in this file.
5. Ask: *"Stage N complete — ready for Stage N+1 ([stage name])?"*
6. Do not proceed until the user says yes.

---

## Confirmed Decisions

These decisions are locked in and must be respected throughout every stage of this project:

- **Drag & Drop persistence**: Customer row reorder is local UI state only. No API call on drag end.
- **URL sync**: Filter state, search query, and pagination (page, pageSize) must sync to URL query params via `nuqs`. Filters must be bookmarkable and shareable.
- **Dark mode**: Dark mode is the default. App ships in dark mode out of the box. Use `next-themes` with `defaultTheme="dark"`. All components must support both themes via Tailwind `dark:` classes.
- **Bonus features**: Bulk actions (bulk delete, bulk status update) and CSV export of filtered results are in scope. Covered in Stage 19.

---

## TypeScript Rules (Non-Negotiable)

These rules apply to every file in this codebase without exception:

- **No `any`**. Ever. Use `unknown` and narrow it, or define a proper type/interface.
- All function parameters and return types must be explicitly typed.
- All API response shapes must be covered by a generic (`APIResponse<T>`, `PaginatedResponse<T>`).
- Use union types instead of enums where possible (e.g., `"active" | "inactive" | "lead"`).
- Prefer `interface` for object shapes, `type` for unions/intersections/aliases.
- No implicit `any` from untyped third-party calls — wrap them with explicit types.
- `as SomeType` casting is acceptable only when the shape is guaranteed (e.g., after Zod parse). Document why when used.

---

## Code Comment Rules

- Only add a comment when the logic is genuinely non-obvious to an experienced developer reading it cold.
- Comments explain **why**, not **what**. The code already says what it does.
- Write comments as if you are the next developer who will maintain this file.
- Do not comment function signatures, variable names, or anything self-evident from the code.
- Do not leave TODO or FIXME comments in committed code. Resolve them before finishing the stage.

Bad — do not do this:
```ts
// fetch customers from API
const customers = await getCustomers(params);
```

Acceptable — non-obvious behaviour that warrants explanation:
```ts
// nuqs serialises arrays as repeated keys (?company=A&company=B),
// but axios serialises arrays with brackets (?company[]=A) by default.
// paramsSerializer aligns axios with the URL format nuqs produces.
const params = new URLSearchParams(searchParams);
```

## Stage 10 — Mutation Hooks
> The three write hooks. Handles cache invalidation, optimistic updates, and toasts.

- [ ] `src/hooks/useCreateCustomer.ts`
  - `useMutation` → `createCustomer`
  - `onSuccess`: `invalidateQueries(["customers"])` + success toast
  - `onError`: error toast
- [ ] `src/hooks/useUpdateCustomer.ts`
  - `useMutation` → `updateCustomer`
  - `onMutate`: snapshot current cache, apply optimistic update to `["customers", id]`

  - `onSettled`: `invalidateQueries(["customers"])`
- [ ] `src/hooks/useDeleteCustomer.ts`
  - `useMutation` → `deleteCustomer`
